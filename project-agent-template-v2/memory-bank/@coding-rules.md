# {{PROJECT_NAME}} — 编码与工程规则

## 1. 通用工程规则

- 一次只实现一个可验收最小增量。
- 不顺手做无关重构或大面积清理。
- 不引入新依赖，除非仓库已在使用或明确批准。
- 修改架构边界、目录职责、跨层数据流时，必须同步更新 `memory-bank/@architecture.md`。
- 任务状态只在对应 playbook 中维护，不在 task index 或其他摘要文档中重复维护。

## 2. 平台/运行时规则

> 按项目平台填写，例如 Android / Web / Backend / Data Pipeline。

通用写法建议：

- 长耗时操作不得阻塞主交互线程或主执行上下文。
- 核心链路必须可观测，至少定义统一性能指标：`{{PERF_METRICS}}`
- 核心失败路径必须有安全回退：`{{SAFE_FALLBACK_RULE}}`
- 与外部系统交互的边界必须有明确错误处理策略。

## 3. 项目特有规则

> 这里写真正与业务/产品相关的不可破坏约束。

示例写法：

- 核心业务输出失败时，必须回退到安全基线结果。
- 遥测/事件命名必须与 `{{EVENT_SCHEMA_PATH}}` 一致。
- 关键业务指标必须使用统一口径采集。
- 涉及人工判断的场景，不得伪装为自动验证通过。

## 4. 交付规则

- 每次交付必须列出改动文件。
- 必须提供复现路径与预期结果。
- 若有人工验证项，必须显式标注“需人工验证”。
- 若改动了规则、任务板或 Ralph 运行契约，应优先同步文档。

## 5. 禁止事项

- 不批量改动与当前任务无关的文件。
- 不隐式改变项目状态真相文件的职责。
- 不把 Ralph backlog 文件当作项目级状态板使用。
- 不把人类必须介入的验证结果写成自动完成。
